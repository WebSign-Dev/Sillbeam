# Upgrade from Core 0.2.0 to 0.3.0

This guide describes the 0.3.0 candidate. Install `^0.3.0` only after the approved
release is available. Local acceptance tests simulate that version; they do not
publish it. See [release status](../../README.md#release-status) and the
[acceptance report](https://github.com/WebSign-Dev/sillbeam-core/blob/3f891afbff43a0ab48af4ec5991f19aa59fe80b0/docs/development/release-0.3.0-acceptance/README.md).

## Package and runtime contracts

```bash
composer require websign-dev/sillbeam-core:^0.3.0
```

The package, namespaces, bundle, attributes, registry interfaces, `sillbeam`
configuration alias and routing type remain unchanged. No descriptor, Module/Project
ownership, host, activation or Doctrine mapping migration is required. PHP/Symfony
constraints remain `^8.4` / `^7.4 || ^8.0`. No new runtime dependency is introduced.
For the older package/namespace rename, use the historical [0.2 guide](0.2.0.md).

Preserve the existing bundle/routing integration, service exclusions and explicit
service overrides. Review broad Symfony service imports with Doctor; make any
needed changes deliberately and merge existing exclusions. Nothing automatically
overwrites existing application configuration. The compatible Flex recipe remains
version `0.2`; upgrading Core does not require a new recipe version or imply a
publicly approved recipe. See [installation](../guides/getting-started.md).

## Diagnostic entry point

To keep diagnostics usable when the container cannot compile, select the existing
Core Console Application in your application's `bin/console`:

```php
use Sillbeam\Core\Console\Application;
```

Keep your existing kernel, Symfony Runtime callback and environment bootstrap.
This explicit developer edit replaces the Symfony Console Application import; it
is not an extra executable. The exact `sillbeam:architecture`, `sillbeam:report`,
`sillbeam:doctor`, `sillbeam:inspect:module` and `sillbeam:graph` commands work before
container boot. Other commands retain Symfony dispatch. See [CLI setup](../reference/cli.md).

```bash
php bin/console sillbeam:doctor
php bin/console sillbeam:doctor --format=json
php bin/console sillbeam:inspect:module Billing
php bin/console sillbeam:inspect:module Billing --project=shop
php bin/console sillbeam:inspect:module Billing -v
php bin/console sillbeam:graph # writes architecture.svg; no extra tools
php bin/console sillbeam:graph --module=Billing --output=billing.svg
php bin/console sillbeam:graph --format=mermaid > architecture.mmd
```

Doctor text remains the default. Its existing exit priority is **2** for unknown or
unexecutable checks, then **1** for action required, then **0** for verified checks.
JSON v1 exposes stable IDs/statuses and concrete details from those same checks;
unknown dynamic configuration stays unknown. See [JSON contract](../reference/doctor-json.md).
Do not interpret exit 0 as an application/service-container health guarantee.

Module inspection accepts an ID or full descriptor class. Shared/private IDs can
collide; use the descriptor or `--project` for private-owner selection. The compact
view merges direct DEPENDS ON/USED BY relationships with declared/observed evidence;
`-v` restores technical detail and original findings. A declared-only relationship
is not necessarily unnecessary; missing observation evidence stays unverified.
`enabled` is not `active`; Project context and global activity remain distinct.
Invalid/incomplete analysis leaves actual activation unknown. Inspection remains
text only, with unchanged exit codes 0/1/2; there is no inspection JSON mode.

Graph output defaults to `architecture.svg` in the current working directory,
rendered directly in PHP without an optional external renderer. Missing parents
are created. Existing regular files require `--force`; symlinks/directories are
rejected. `--module` retains direct incoming/outgoing relationships only;
`--project` selects ownership/activation context and retains incident boundary
violations. Scripts needing Mermaid must pass `--format=mermaid`; STDOUT then
contains raw source and `--output`/`--force` are not accepted. Unknown state and
partial evidence remain explicit. Successful exports retain analysis exit codes
0 valid / 1 violations / 2 unavailable; invocation/selection errors use 3 and SVG
output failures 4. See the [graph contract](../reference/mermaid-graph.md).

## Documentation tooling

Core contributors may run `composer docs:build` and open
`build/docs/api/index.html`. phpDocumentor 3 is a development tool, with only its
shim plugin allowed. Public HTML excludes `@internal` declarations. Generated
HTML, cache and local config overrides are ignored; do not commit them.
Run `composer docs:export-json` manually to write the English public API file
`build/docs/api/sillbeam-core.en.json` ([schema/contract](../reference/phpdoc-json.md)).
The existing phpDocumentor data supplies plain descriptions and original signatures/
code examples. No translation, synchronization, website integration or release hook
runs. The HTML command remains independent. Applications do not inherit Core's
root-only development dependencies.

## Deployment checks

Run the application's tests, Doctor and architecture validation, then build a
fresh production cache through the normal CLI deployment process. Do not rely on
a cold HTTP request to compile a container. Non-debug production HTTP continues
to require a prebuilt cache and must not start AST/architecture analysis.
Native Console inspection can read an existing compiled snapshot; the Core adapter
prepares fresh analysis using the existing kernel configuration hooks.

No automatic install/repair command, compatibility alias or new architecture rule
is introduced in 0.3.0. Final release approval is a separate maintainer decision.

## Development versions and approval

Use branch `dev-v0.3.x` for current development. Composer prefixes that branch with
`dev-`, so its alias key is `dev-dev-v0.3.x` → `0.3.x-dev`. The `dev` and `main`
aliases preserve the same development line. Stable `^0.3.0` still requires an
approved published release; use an explicit development stability constraint only
when intentionally testing unreleased source.

Promotion order: development → `dev` (automatic CI) → maintainer approval → `main`
(automatic CI) → explicitly authorized release. Push triggers remain `main`/`dev`
only; neither a development push nor a PR automatically runs this workflow.
