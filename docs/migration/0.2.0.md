# Upgrade to Sillbeam Core v0.2.0

Sillbeam Core v0.2.0 changes technical identity, aggregates existing architecture findings, adds container-independent reporting and separates build validation from production HTTP. It retains Module/Project boundary semantics, adds unresolved application-class checks and improves diagnostic guidance; no Frame or Components features are included. The package is registered on Packagist. Stable installation requires the corresponding `v0.2.0` version to be listed; see [release status](../../README.md#release-status). A local Composer path repository remains available for source-based integration tests.

| v0.1 | v0.2 |
| --- | --- |
| `websign-dev/sillbeam` | `websign-dev/sillbeam-core` |
| `WebSign-Dev/Sillbeam` | `WebSign-Dev/sillbeam-core` |
| `Sillbeam\` | `Sillbeam\Core\` |
| `Sillbeam\SillbeamBundle` | `Sillbeam\Core\SillbeamCoreBundle` |
| `Sillbeam\DependencyInjection\SillbeamExtension` | `Sillbeam\Core\DependencyInjection\SillbeamCoreExtension` |
| Flex `websign-dev/sillbeam/0.1` | Flex `websign-dev/sillbeam-core/0.2` |

1. Replace the old dependency in your application's `composer.json` with `"websign-dev/sillbeam-core": "^0.2.0"`, then update Composer's lockfile. Do not install both packages together. The new package does not declare `replace` or silently alias the old APIs.
2. Replace every `Sillbeam\` PHP prefix with `Sillbeam\Core\` in imports, attributes, fully qualified names, service definitions, compiler passes, tests and custom integrations. Rename the bundle and extension references as shown above. Application namespaces remain unchanged. If using the optional kernel, its new name is `Sillbeam\Core\Kernel\SillbeamKernel`.
3. Replace the bundle entry in `config/bundles.php`:

   ```php
   Sillbeam\Core\SillbeamCoreBundle::class => ['all' => true],
   ```

4. Review Flex removal/install diffs before accepting generated changes. The local recipe registers only the new bundle and retains `config/routes/sillbeam.yaml`. Preserve application-specific route/configuration edits and remove the old bundle registration. The recipe is locally prepared; its availability depends on your Flex endpoint and is independent of package publication.
5. Clear Symfony's cached containers and routes in each environment, regenerate autoload files, warm the cache and run your application tests. Check `bin/console sillbeam:about` and `bin/console sillbeam:architecture`.

The configuration root and extension alias remain **`sillbeam`**, including `config/packages/sillbeam.yaml`. Keep CLI names `sillbeam:*`, the route import type `sillbeam`, and named service IDs such as `sillbeam.module_registry` and `sillbeam.project_registry`. Class-based autowiring IDs move with their PHP classes into `Sillbeam\Core\`; update explicit references to those IDs as well.

Module/Project discovery, ownership, activation and declared dependency boundaries, routing, native Symfony service integration and optional Doctrine mappings retain their established semantics. Static reference analysis is expanded: `code.unknown_class` can report unresolved application-owned classes that v0.1.0 did not flag, including in inactive code and descriptor constructors. Review these findings and their source evidence when upgrading. No database schema or data migration is required by the technical rename. Historical v0.1 release notes and verification snapshots retain their original names and version evidence.

The canonical repository is `WebSign-Dev/sillbeam-core`; update an old local origin URL if needed. Package registration is complete. Stable release tagging and the outstanding external Recipes Contrib review are separate from application migration; these instructions do not perform publication actions.

## Validation, reporting and production rollout

The configuration model and architecture boundaries stay the same. Existing independent violations are now collected in `ArchitectureAnalysisResult` with stable rules/severities/context. Invalid container builds throw `ArchitectureValidationException` (still a `LogicException`); consumers parsing exception text must migrate to structured findings. Fatal blockers preserve earlier findings but cannot expose a valid runtime graph.

For reports even when the service container cannot compile, replace only the existing Console Application import in `bin/console` with `Sillbeam\Core\Console\Application`. Preserve the application's existing kernel, Runtime, environment and bootstrap. See [CLI setup](../reference/cli.md). The ordinary FrameworkBundle Application still supports reports after successful boot, but cannot report around its own failed boot.

Use `sillbeam:architecture --format=json` for automation. JSON schema version 1 includes module/Project information, validity/completeness and findings; available remediation appears in `context.suggestion`. Exit codes are 0 (valid), 1 (architecture violations), 2 (analysis unavailable/fatal or invalid configuration/usage). Consumers should allow optional context fields and must stop a build on every nonzero result. A valid architecture report does not prove an unrelated Symfony service configuration is valid: perform both report and container build checks.

Production now requires a prebuilt container with debug disabled. A non-debug HTTP request cannot compile a missing container: it returns a generic 503 before Sillbeam source analysis. Existing warm production requests use compiled registries/services/routes/mappings without source analysis. The policy uses `kernel.debug`, not the environment name alone. Debug mode validates on cold/rebuilt containers and follows Symfony source/config resource tracking.

Create a fresh cache/build directory for each immutable release, run `APP_ENV=prod APP_DEBUG=0 php bin/console cache:clear`, `cache:warmup`, and `sillbeam:architecture --format=json`, and only activate the release after all succeed. Cache clear/warmup also perform fresh architecture checks with an existing cache and with `--no-warmup`/`--no-optional-warmers`. A successful `--no-warmup` does not make the release ready to serve HTTP. Do not replace sources underneath a running production cache. See the [validation lifecycle](../reference/architecture-analysis.md#development-and-production-lifecycle).

## CLI output and installation checks

Text output now follows prototype 1.2: related findings become diagnoses, with a
compact index and the first diagnosis expanded by default. `--all` expands every
group, `--issue=N` selects a run-local group and `-v` shows technical details.
Migrate scripts that parse former terminal tables/groups to `--format=json`.
JSON retains schema version 1 with additive optional Application Coupling evidence;
strict consumers must allow those fields. `--couplings` is opt-in for text and
Markdown and does not introduce dependency rules or change exit codes.

`sillbeam:report` writes a standalone Markdown document, including the shared
explanations and complete Technical Evidence, even when analysis is invalid or
incomplete. Use its exit code and completeness status; a written file is not a
successful architecture approval.

The new `sillbeam:doctor` checks installation files statically without repairs or
configuration execution. Dynamic/ambiguous cases require manual review, and
conventional Runtime callbacks and stock Symfony 7.4/8.1 kernels are supported.
Unknown routing no longer hides independently proven service overlaps; mixed
known conflicts and unresolved details are both shown, retaining exit-2 precedence.
See the [F01/F02 follow-up](../development/doctor-f01-f02-verification-2026-10-25/README.md) to the unchanged original acceptance.
Doctor does not replace architecture validation or Symfony checks.
With the Core adapter it runs before kernel boot; ordinary Symfony boot can write
cache files before the command starts.

The recipe is technically prepared and locally tested, with separate
`post-install.txt` instructions. The package is registered on Packagist. Public
Recipes Contrib approval remains the outstanding external integration. Automatic
installation also requires a matching stable package version and endpoint
availability; a Core tag alone does not enable it. It never changes `bin/console` or native service imports. Preserve
those application settings and apply the required manual integration yourself.
