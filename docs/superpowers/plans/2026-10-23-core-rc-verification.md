# Core v0.2.0 RC verification plan

Goal: verify the existing release candidate end to end and compare its build/request costs with equivalent native Symfony behavior. No new runtime features, Frame/Components changes, publication, tags, commits or pushes.

- [x] Audit identity/conventions, Modules/Projects, finding aggregation, broken-container reporting, CLI/schema/exit codes and dev/prod lifecycle against tests and current documentation.
- [x] Extend tools/benchmark-architecture.php using paired disposable applications with identical services, dependency chains, controllers/routes and response assertions. Native Symfony registers the same application behavior explicitly, without loading SillbeamBundle. Use 10/50/100 modules in dev/prod; separate subprocesses for cold compilation, warm boot and warmed HTTP batches; report sample counts, nearest-rank p50/p95, peak allocated PHP memory, environment details and raw JSONL. Retain architecture phase measurements separately from fair application comparisons. Never preparse application sources before cold build measurement.
- [x] Add benchmark smoke coverage asserting paired workloads, all metrics, valid HTTP and absent production analyzer. Run reduced smoke before full benchmark. Warm HTTP uses Kernel::handle, not network latency; record this limit explicitly.
- [x] Run all available CI commands, full supported local PHP/Symfony matrices, isolated consumer/Flex/no-dev archive installation; identify unavailable CI execution separately from local equivalents. Fix reproducible in-scope failures with regression tests.
- [x] Run the full benchmark without competing test jobs. Preserve raw measurements and document methodology, measured deltas and limits without extrapolating advantages.
- [x] Update migration beyond technical rename, changelog, test/release documentation and compact RC evidence/blocker report. Verify style/static/architecture checks after changes.

Execution notes: all seven RC areas were mapped to existing test evidence. Raw results and reviewed methodology are committed-ready documentation; no runtime feature/config changes, commit or remote writes were performed. Hosted CI and public package/repository/recipe availability remain unverified release gates.
