# Sillbeam Core v0.3.0 — release candidate

Core 0.3.0 builds on 0.2.0 with documentation and developer diagnostics. This
checkout prepares release acceptance; it is not a published version or final
release approval. Read the [initial acceptance evidence (2026-10-29)](https://github.com/WebSign-Dev/sillbeam-core/blob/3f891afbff43a0ab48af4ec5991f19aa59fe80b0/docs/development/release-0.3.0-acceptance/README.md)
for its original commands, failures, risks and recommendation. Its matrix results
precede later graph, inspection and export refinements; see the current scope below.

## Included work

- English PHPDoc for public contracts and relevant internals, deliberate `@api` /
  `@internal` boundaries, PHPStan-compatible types, and an HTML API build through
  development-only `phpdocumentor/shim`. Run `composer docs:build`; generated
  output/cache remains ignored. See [public API](../reference/public-api.md).
- Manual `composer docs:export-json` writes English public API documentation to
  `build/docs/api/sillbeam-core.en.json` with [schema version 1](../reference/phpdoc-json.md).
  It reuses phpDocumentor descriptors, preserves signatures/code examples and plain
  translatable descriptions, excludes internal API, and retains the HTML build.
  Translation and website integration are manual downstream work; there is no
  synchronization, publication, release hook or production export on CI push.
- Clearer Composer/Flex → Doctor → first module guidance and static Doctor
  diagnoses for bundle/routing/service-import/Console-adapter integration.
  Existing application files are changed only by an explicit developer decision.
  No `sillbeam:install` command or alternative installation system is added.
- `sillbeam:doctor --format=json` with [schema version 1](../reference/doctor-json.md),
  stable check IDs, statuses and diagnosis details. Text remains the default;
  existing status/exit priority (2 before 1 before 0) remains unchanged.
- `sillbeam:inspect:module Billing` shows compact state/scope/Project context,
  architecture status and merged DEPENDS ON/USED BY rows with evidence labels.
  `Declared only` is not an unused-dependency finding; incomplete observation stays
  unverified. `-v` adds configuration, full classes/paths, activation evidence,
  separate relations, reference locations and original findings/context. ID/class
  selection and `--project` ambiguity handling are unchanged; output remains text only.
- `sillbeam:graph` writes `architecture.svg` directly in PHP, without extra tools, with compact
  module labels, `--module`/`--project` filters, `--output` and deliberate `--force`
  replacement. `--format=mermaid` exports deterministic raw source with direct
  declared dependencies, observed undeclared references, disabled configuration,
  recorded cycle members, private ownership and validated Project memberships.
  Missing output directories are created automatically; no external renderer is required.

The last two commands reuse ArchitectureReport and the existing analyzer results.
Doctor JSON serializes InstallationInspector results; it does not perform a second
set of checks. Invalid/incomplete architectures remain diagnostic evidence; unknown
activation/reference evidence is never presented as a validated runtime graph.
Both commands are also available through the existing Core Console adapter before
container compilation. See the [CLI reference](../reference/cli.md).

## Compatibility and upgrade

The package, `Sillbeam\Core\` namespace, bundle, configuration alias, routing type,
registry contracts and runtime activation rules remain unchanged from 0.2.0.
No new runtime dependency, discovery path, parser pass or architecture rule is
introduced. phpDocumentor is development-only. PHP remains `^8.4`, Symfony remains
`^7.4 || ^8.0`; the maintained test matrix selects PHP 8.4/8.5 and Symfony 7.4/8.1.
Declared dependency ranges alone do not prove every combination was tested.

Use the [0.2 → 0.3 upgrade guide](../migration/0.3.0.md). Human-readable module inspection changed layout, and graph output defaults to an
SVG file. Scripts consuming Mermaid must pass `--format=mermaid`; scripts parsing
inspection text must adapt. Use documented architecture/Doctor JSON where available,
not terminal layout. Module inspection has no JSON mode; Mermaid remains raw source.
Graph analysis exits remain 0/1/2 after export; invocation/selection uses 3 and
SVG output failures use 4.

## Packaging and availability

Release test scripts simulate 0.3.0 locally from copied source or a real Composer
ZIP. They do not create a tag or publish to Packagist. The current branch is `dev-v0.3.x`; its Composer name `dev-dev-v0.3.x`, plus
`dev-dev` and `dev-main`, alias to `0.3.x-dev`. Release versions remain derived from
Git tags; the aliases do not publish a stable version.
The existing compatible Flex recipe stays under `0.2/` and is not re-versioned.
Package publication and public recipe availability remain separate external steps.

## Verification scope and release flow

The existing 2026-10-29 report is historical evidence for its recorded snapshot,
including its original local matrix and now-superseded development-branch CI trigger.
It is not a fresh matrix certificate for subsequent refinements. Current behavior
is defined by the [graph](../reference/mermaid-graph.md),
[module inspection](../reference/module-inspection.md) and
[PHPDoc JSON](../reference/phpdoc-json.md) contracts. Local verification and a configured
workflow do not establish a successful remote run on the final release commit.

Required order: **`dev-v0.3.x` → `dev` with automatic CI → maintainer approval →
`main` with automatic CI → explicitly authorized release**. The unchanged workflow
runs on pushes to `main` and `dev` only, plus manual dispatch. It has no PR trigger
and no automatic push CI on `dev-v0.3.x`. Neither a green run nor an earlier local GO
recommendation is a release authorization. See [contribution flow](../../CONTRIBUTING.md#submit-a-pull-request).

## Operational limits

Production non-debug HTTP still requires a prebuilt container. Cold HTTP requests
must not compile/analyze source; deployment must build/warm caches before serving
traffic. Warm HTTP uses compiled state. Native Symfony diagnostics require a
compilable container; select `Sillbeam\Core\Console\Application` to diagnose a broken
architecture. Native warm-container diagnostics reflect their compiled snapshot.

Doctor is conservative and static. Dynamic/ambiguous configuration remains
`not verified`; no repair or application-file overwrite is performed. Project
boundaries are architecture organization, not security/tenant isolation. Incomplete
source evidence cannot prove dependency absence or actual activation. The Mermaid
export is not a live service health check or a visual renderer.

Historical 0.2.0 reports and release notes retain their own results and findings.
Final release authorization belongs exclusively to the maintainer.
