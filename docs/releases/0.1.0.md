# Sillbeam 0.1.0 — draft release notes

Status: prepared first public release; not tagged or published. The proposed version is 0.1.0, consistent with `0.1.x-dev`, the skeleton's `^0.1` requirement and the Flex recipe's `0.1/` directory.

Sillbeam is a Symfony module architecture layer. Modules declare their dependencies; optional Projects compose shared and private modules. Discovery and validation run during the Symfony container build. Conventional Symfony code remains supported alongside these areas.

## Included

- Configurable discovery roots, namespaces and exclusions; immutable Module/Project catalogs and active graphs.
- Validation of ownership, unknown targets, cycles, forbidden private-module access and undeclared static cross-module references.
- Native Symfony service attributes, autowiring, autoconfiguration, controller routing and explicit application overrides.
- Optional DoctrineBundle mapping integration for active modules and direct Project entities, preserving native mappings.
- Host-based Project routing and request context; `sillbeam:architecture` text/JSON and `sillbeam:about` diagnostics.
- Six supported layouts: Symfony-only, Modules-only, Project-only, Single-Project, Multi-Project and Hybrid. Either the standard Symfony kernel or optional SillbeamKernel can be used.

## Installation

Requires PHP `^8.4`, Composer 2 with runtime API `^2.2`, and Symfony `^7.4 || ^8.0`. Doctrine is optional; the integration has been tested with DoctrineBundle 3.3.2 and ORM 3.7.5.

After publication in an existing Symfony application:

```bash
composer require websign-dev/sillbeam:^0.1
```

Until publication, install `dev-main` from a local path/VCS repository. Register SillbeamBundle and the central configuration/route import as shown in the [README](../../README.md#quick-start). Flex recipe availability is separate from the PHP package; manual setup works without it. The repository's [skeleton](https://github.com/WebSign-Dev/Sillbeam/blob/main/skeleton/README.md) is a directory template, not a separately published runnable create-project package.

## Known limitations

- Projects share one container, event system and database. They do not isolate tenants or automatically host-scope subscribers/handlers.
- Static validation covers actual PHP class references between module areas. Dynamic class strings, PHPDoc, string service IDs, ordinary Symfony code and direct Project code are outside that analysis. Explicit native imports remain application-controlled.
- With Projects, unassigned shared modules remain catalogued but inactive. Active graphs cannot require disabled modules.
- Unknown Project hosts throw `OutOfBoundsException` from registry/context lookups. Native Hybrid routes can still serve those hosts and must handle that exception if they ask for Project context. CLI has no current Project without a Request.
- Activation/configuration changes require rebuilding production container caches. No persistent discovery cache or runtime hot activation is promised.
- No authentication, API framework, entity bases, stores, generators or Foundation facilities are included. Former private development APIs require [migration](../migration/modular-monolith.md).
- This is a pre-1.0 API. Future incompatible changes will be documented; no long-term support or response-time commitment is made.
