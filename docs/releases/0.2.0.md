# Sillbeam Core v0.2.0 — unreleased

Sillbeam Core is a module architecture layer for existing Symfony applications
and modular monoliths. Modules declare their boundaries and dependencies;
optional Projects compose shared and private modules. Symfony continues to own
the container, services, routing and HTTP runtime. Doctrine mapping integration
is optional, and the standard Symfony kernel is sufficient.

Version 0.2.0 combines a breaking technical rename with a substantially clearer
developer workflow: architecture checks explain what failed, why it matters and
which correction or design decision comes next. It also adds standalone reports,
minimal descriptor generators and a static installation inspector. These features
are implemented in the development branch; **this version remains unreleased**.
No package publication, release tag or external recipe approval is asserted here.

## From a finding to a useful next step

Compared with v0.1.0, architecture analysis collects independent violations into
structured findings and distinguishes them from errors that prevent complete
analysis. The shared Diagnostic Engine turns related findings into diagnoses
without losing their original evidence. CLI output and Markdown use the same
explanations and context-aware resolutions.

For example, a class reference from one module to another may need a declared
dependency. The explanation identifies the relevant modules, source locations and
descriptor. It considers the declared graph, privacy and activation before offering
a dependency edit: adding an edge that would create a cycle is not presented as a
safe fix. Disabled, unassigned and unknown targets receive different guidance.
Moving a contract or changing dependency direction remains a design option for
the developer to evaluate, rather than an automatic repair.

When advice can identify a concrete descriptor, PHP references remain fully
qualified `::class` expressions. A similarly named entity or service must not
silently become the suggested module descriptor. Incomplete analysis is explicit:
fix the blocker and rerun before trusting activation or graph conclusions.

The implementation also detects unresolved application-owned static classes via
`code.unknown_class`, with file/line evidence, including in inactive module code
and descriptor constructors. Composer/discovery ownership distinguishes local
application types from external dependencies. This can expose issues that were
not reported by v0.1.0. It does not replace PHPStan or analyze arbitrary dynamic
class strings, PHPDoc types or application-wide access control.

## A CLI designed for diagnosis

Text output follows CLI prototype 1.2. A clean result is short. One diagnosis is
explained in full; with several diagnoses, the complete compact index precedes
the first explanation. Findings and diagnoses are counted separately. Locations
are readable by default; verbosity exposes rule codes and technical evidence.

```bash
php bin/console sillbeam:architecture
php bin/console sillbeam:architecture --all
php bin/console sillbeam:architecture --issue=2 -v
php bin/console sillbeam:architecture --couplings
php bin/console sillbeam:architecture --format=json
```

`--issue=N` selects a diagnosis group from that run, not a persistent issue ID.
`--all` and `--issue` are mutually exclusive. JSON always includes the complete
schema-version-1 result and cannot be combined with these text selectors or
`--couplings`. Application Couplings are informative references from modules to
indexed application code outside module areas; they are opt-in in text/Markdown,
do not become declared dependency edges, and do not change architecture validity.
JSON retains version 1 with additive optional coupling evidence fields.

Architecture/report exit codes are **0** for valid analysis, **1** for violations
and **2** for incomplete/unavailable analysis, invalid usage or a report write
failure. A valid architecture result does not certify the whole Symfony container.

To diagnose an application whose container cannot compile, manually select:

```php
use Sillbeam\Core\Console\Application;
```

Replace only the Application import in the existing `bin/console`; preserve its
Runtime/Dotenv bootstrap and kernel construction. This existing adapter runs the
exact `sillbeam:architecture`, `sillbeam:report` and `sillbeam:doctor` commands
before kernel boot. Commands such as `list`, generators and ordinary Symfony
inspection commands still require the regular container path. The adapter is not
a second executable or a way to bypass invalid configuration-loading hooks.
See the [CLI reference](../reference/cli.md) for setup and supported options.

## Share a standalone architecture report

```bash
php bin/console sillbeam:report
php bin/console sillbeam:report --output=docs/architecture-report.md
php bin/console sillbeam:report --couplings --output=architecture-report.md
```

The default destination is `architecture-report.md` in the application's project
root. Relative destinations use that root; the parent directory must exist.
The report is a document for review, not a copy of the terminal screen:

- An overview presents modules, Projects, activation and dependencies by readable
  names, with Project hosts and explicit unknown states where necessary.
- Every diagnosis includes its explanation, impact and next steps from the shared
  engine; design options remain identifiable as choices.
- A separate **Technical Evidence** section retains descriptor identities, rule
  codes, original messages, full paths and finding context. Optional Application
  Couplings stay in their own informational appendix.

Version/time/status and analysis completeness make the document usable outside
the terminal. Reports can be written when analysis finds violations or is
unavailable, retaining exit 1 or 2; incomplete catalogs never imply an approved
graph. Replacement is atomic and a failed write preserves the previous report.
See the [reporting guide](../guides/architecture-reporting.md) and
[analyzer-backed examples](../examples/architecture-reports/README.md).

## Install and create the first descriptors

After package publication, install with:

```bash
composer require websign-dev/sillbeam-core:^0.2.0
```

Until then, the recorded consumer tests use an explicit local Composer path
repository and copied package source. Manual integration registers
`Sillbeam\Core\SillbeamCoreBundle` and imports routing type `sillbeam` once.
No `config/packages/sillbeam.yaml` is needed for defaults. Review broad native
service imports so they exclude Module/Project discovery areas when Sillbeam
should control their activation; preserve existing exclusions and explicit services.
See [getting started](../guides/getting-started.md).

The locally finalized Flex recipe performs bundle registration and route import,
with follow-up instructions in `post-install.txt`. Its source and actual output,
installation with/without Doctrine and removal have been locally tested.
**A prepared recipe is not a publicly available Recipes Contrib recipe.**
Packagist availability with a matching published version, external Symfony
validation/review/approval, endpoint availability and consumer Contrib/plugin
permission are separate prerequisites. Releasing Core v0.2.0 alone does not
activate the recipe.

The recipe deliberately edits neither `bin/console` nor existing Symfony service
imports. Those are manual integration decisions. On uninstall, Flex owns the
recipe route filename, including a pre-existing file at that destination; preserve
custom content before removal. Other application-owned configuration is retained.
See [Flex installation and submission](../guides/flex-recipe.md).

```bash
php bin/console sillbeam:doctor
php bin/console sillbeam:make:module user
php bin/console sillbeam:make:project shop
php bin/console sillbeam:make:module checkout --project=Shop
php bin/console sillbeam:architecture
```

Generators create only a directory and minimal descriptor file, using the resolved
roots and namespaces. Only an initial lowercase ASCII letter is uppercased:
`user` becomes `User`, `userProfile` becomes `UserProfile`. Invalid names and
existing targets are rejected; controllers, services, entities and configuration
are not generated. Discovery and activation remain separate, and multiple
Projects still require their host configuration. These commands require a
compilable container.

### What Doctor can verify

`sillbeam:doctor` is a **static, read-only installation check**. Its implementation
does not boot the kernel, execute application configuration or repair files.
It distinguishes `verified` static evidence, `action required` and `not verified`.
Dynamic or ambiguous configuration requires manual review and must not be treated
as verified. Exit **0** means supported checks verified, **1** means action required,
and **2** means a check could not be verified or run; 2 takes precedence over 1.
It replaces neither architecture analysis, PHPStan nor Symfony configuration checks.

The original independent acceptance found two Doctor defects, now corrected:
normal Symfony Runtime callbacks resolve the returned Application and its imports,
including aliases/FQCNs; standard Symfony 7.4/8.1 kernels and the existing
`SillbeamKernel` convention are recognized statically. Unknown routing no longer
masks a separately proven service-import conflict. A check with a known conflict
and independent unknown details displays both results while retaining exit 2.

Unknown route overlays, dynamic container imports, custom hooks and ambiguous
bootstraps still need manual review. A correct adapter does not make every
configuration verifiable or guarantee exit 0. See the
[F01/F02 follow-up verification](../development/doctor-f01-f02-verification-2026-10-25/README.md).

Use the adapter above for inspection without container boot, including with
invalid architecture. The regular Symfony entry point boots first and can write
ordinary cache files before Doctor starts. The implementation's read-only behavior
does not remove those framework bootstrap effects. See
[Doctor behavior and exit codes](../reference/cli.md#installation-doctor).

## Breaking changes and operational requirements

| v0.1.0 | v0.2.0 |
| --- | --- |
| `websign-dev/sillbeam` | `websign-dev/sillbeam-core` |
| PHP prefix `Sillbeam\` | PHP prefix `Sillbeam\Core\` |
| `Sillbeam\SillbeamBundle` | `Sillbeam\Core\SillbeamCoreBundle` |
| `Sillbeam\DependencyInjection\SillbeamExtension` | `Sillbeam\Core\DependencyInjection\SillbeamCoreExtension` |

No compatibility aliases are provided. Update imports, attributes, explicit class-
based service IDs, custom integrations and the optional `SillbeamKernel` reference.
The `sillbeam` configuration alias, existing command names, routing type and named
service IDs stay stable. Module/Project boundaries and activation semantics remain;
static class analysis is expanded as described above. The human-readable CLI
layout changes; use JSON rather than parsing terminal output. Repository identity
migration and publication remain separate from the implemented PHP/package rename.

Production HTTP with debug disabled now requires a prebuilt container. A request
that would need compilation receives a generic 503; warm requests use compiled
state without fresh Sillbeam source analysis. Development/debug mode follows
Symfony resource tracking and validates cold/rebuilt containers. CLI builds remain
strict, and cache clear/warmup recheck current sources even with warm caches.
Deploy into a fresh release cache, stop on nonzero analysis/build results, and warm
it before serving traffic. `--no-warmup` alone is insufficient. See the
[upgrade and rollout guide](../migration/0.2.0.md).

## Requirements, evidence and remaining gates

Package constraints remain PHP **`^8.4`**, Composer runtime API **`^2.2`** and
Symfony **`^7.4 || ^8.0`**. DoctrineBundle is optional. The current CI targets PHP
8.4/8.5 and Symfony 7.4/8.1; a declared version range is not proof that every
combination was independently tested. Projects share Symfony infrastructure and
do not provide tenant/security isolation. Core does not include Frame/Components
features or automatically fix architectural design.

The [independent installation acceptance of 2026-10-25](../development/installation-acceptance-2026-10-25/INSTALLATIONS-ABNAHME.md)
is present and has been reviewed for these notes. It records:

- **542 tests / 6050 assertions**, passed in the isolated PHP-8.5.4 run using
  copied root dependencies (Symfony 8.1.6).
- Fresh consumer scenarios on Symfony 7.4.21/8.1.9 with PHP 8.5.4, plus separate
  PHP-8.4.26 runtime checks using those resolved dependencies; no independent
  Composer resolution under PHP 8.4 is implied.
- Working architecture diagnosis, Markdown reports, module routes, production
  HTTP controls, Doctrine roundtrips and recipe removal, alongside the Doctor
  limitations described above.

Its historical verdict is **not an unconditional release approval**. The linked
follow-up verifies the F01/F02 corrections; F03 remains an operational limit and
records the ordinary Symfony bootstrap's cache writes. Its dated public checks
returned 404 for the Packagist package metadata and Contrib recipe endpoint.
No subsequent publication or external approval is asserted here.

The [Flex verification record](../development/flex-recipe-verification.md),
[diagnostic communication checks](../development/cli-communication-verification.md)
and [earlier RC evidence](../development/core-rc-2026-10-23.md) provide separate,
scoped results. Earlier compatibility/benchmark snapshots are not a substitute
for final acceptance and do not establish a general performance advantage.

**v0.2.0 remains unreleased.** Review the follow-up evidence and remaining limits,
complete release verification and coordinate package/recipe publication separately.
